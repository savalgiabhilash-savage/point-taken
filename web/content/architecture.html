01

Overview

  • FPL Selector is a personal Fantasy Premier League assistant
  • It pulls FPL data (this season and last), bookmaker odds, cup and European fixtures, news and predicted line-ups
  • A transparent rules-based model projects expected points (xPts) for every player in every remaining gameweek
  • A mixed-integer optimizer then recommends transfers, captain, hits and chip timing for your squad
  • A news layer and a grounded Claude chat assistant sit on top

DocsThis page. Visible only to the owner account.
  • Design principles (from CLAUDE.md):
    • Every xPts number is a sum of stored, named components
    • Minutes come first
    • Underlying stats are opponent-adjusted and shrunk toward position averages
    • Recommendations reason about your real team state (bank, free transfers, chips)
    • Every model change is backtested on RMSE before it ships; live-only factors (news, line-ups, set pieces) learn their weight from outcomes

06

Crosswalk & custom FDR

FPL ↔ Understat player matching (crosswalk.py)

  • No shared ID exists, so names are fuzzy-matched after ASCII-folding
  1. Team pass. Candidates are restricted to the player's club, with five team names mapped (Man City, Man Utd, Newcastle, Nott'm Forest, Spurs). Score = max of token_sort_ratio on full name and web name, and partial_ratio on web name when it has 5+ letters. A surname match plus a compatible first name raises the score to 91. Accept if the score is ≥ 85 and beats the runner-up by ≥ 6.
  2. Global pass (summer transfers): full-name token_sort_ratio ≥ 92 against all Understat players, margin ≥ 8.
  3. Anything else goes to reports/crosswalk_review.csv. The last run matched 396 players (51 via the global pass) and left 271 unmatched: 162 low score, 108 at promoted clubs, 1 ambiguous.
  • Every run clears understat_id first, so dropped matches don't linger

Custom fixture difficulty (fdr.py)

  • Team xG for and against per game pools 2025/26 Understat (38 games at half weight) with this season's FPL numbers: xG for = Σ players' expected_goals, xG against = Σ players' expected_goals_conceded ÷ 11, because all 11 players on the pitch accrue every chance conceded
  • Team rating = xG for − xG against
  • Promoted clubs use this season alone, or the weakest returning team's rating before their first game
  • For each fixture, difficulty = 1 + 4 × (opponent rating − min) / (max − min), then −0.25 at home and +0.25 away, clamped to 1–5
  • Current range: Arsenal +1.17 (hardest opponent) down to Sunderland −0.45
07

The xPts model (model.py, rules-v6)

  • For every player and every fixture in the horizon, the model computes eight components and sums them
  • Double gameweeks sum both fixtures
  • Blank gameweeks write no row
  • The next GW is FPL's is_next event (the next deadline), and the pipeline writes every GW from there to GW38
  • Each run also deletes projections for GWs that have started, so "lowest GW in projections" is always the next deadline

1. Minutes

availability = 0            if status in {i, s, u, n}
             = chance/100   if chance_of_playing_next_round is set
             = 0.5          if status = d
             = 1.0          otherwise
news_adj     = Claude minutes_risk_adj × topic weight × freshness     (≤ 0)
               topic: injury/suspension 1.0 · rotation 0.75 · transfer/off-pitch 0.5 · other 0
               freshness: 1 up to 3 days old, fading to 0 at 14 days
availability = min(FPL availability, 1 + news_weight × news_adj)      news never stacks on FPL's flag
history      = last 8 finished GWs in which the player's club played: {games, starts, minutes}
w(GW)        = 0.5 ^ (GWs ago / 3)                                  recent games count most
prior        = min(1, last_season_understat_minutes / 2600)          (none if unmatched)
start_rate   = (Σw·starts + 0.5·prior) / (Σw·games + 0.5)             prior alone before any game
p60_start    = share of full-start GWs with 60+ min     }  each shrunk toward its default
start_mins   = average minutes in those starts          }  (0.88, 85, 0.15, 20 min)
cameo_rate   = share of non-start GWs with a sub cameo  }  by 3 virtual games
cameo_mins   = average cameo minutes                    }
return ramp  = regular starter (pre-absence rate ≥ 0.6) back from 2+ missed games, flag clear:
               start_rate += w_return × (0.7 × pre-absence rate − start_rate)           (factor 5, learned)
congestion   = × 0.92 if his club has another match (any competition) within 3 days    (factors 6-7)
line-up      = next GW only: p_start += w_lineup × confidence × (0.92 if named / 0.10 if left out − p_start)
manager      = after a managerial change, older games and last season count half        (factor 14)
p_start      = availability × start_rate × congestion  (then the line-up adjustment)
p_cameo      = (1 − p_start) × cameo_rate      (0 if unavailable)
p_play       = min(1, p_start + p_cameo)
E[minutes]   = p_start·start_mins + p_cameo·cameo_mins
p_60         = p_start · p60_start
  • Live, the history comes from FPL's event/{gw}/live (one call per GW, 8 per run); in the backtest, from the dataset rows
  • Only GWs where the player's current club played count, so a club blank isn't read as being dropped
  • The half-life (3 GWs) and prior strength (0.5 games) were tuned on 2023/24 and confirmed on the held-out 2024/25 and 2025/26

2. Role share and form (form_model.py)

team_xg_on   = his team's xG in each game × his minutes / 90     (what his team made while he played)
xg_share     = (Σ his xG + 2 × position avg share) / (Σ team_xg_on + 2)     this season + last season (weight 1.0)
xa_share     = same with his xA
bonus90      = (Σ bonus + 6 × position avg) / (Σ minutes/90 + 6)
yellow90     = same with yellow cards
recency      = off (0.5 ^ (GWs ago / half-life) built in; half-lives 4–16 didn't improve accuracy)
home/away    = off (own home and away shares built in; no measurable gain)
  • A share is measured against what his own team created in each game, so it is opponent-adjusted: a big night against a weak side doesn't inflate it.
  • "Last season" is the FPL (Opta) dataset (fpl_history.py, vaastav 2025/26), matched by FPL's stable player code. It covers every player and is the same source the backtest replays. It replaced Understat player priors, so the 40% of players without an Understat match now have real history.

3. Per-fixture components

xG_for, xG_against = this fixture's expected goals for / against the team   (team model, below)
adj          = xG_for / team's expected goals vs an average opponent       (shown as "attacking outlook")
x_goals_pts  = xg_share · xG_for · form · (E[min]/90) · GOAL_PTS[pos]      GK 10, DEF 6, MID 5, FWD 4
x_assist_pts = xa_share · xG_for · form · (E[min]/90) · 3
penalties    = taker: + w_pen × 0.14 × (xG_for ÷ league avg) × (E[min]/90) × 0.78 goals     (factor 3, learned)
set pieces   = corner taker + w_sp × 0.06 xA/90, direct-FK taker + w_sp × 0.02 xG/90, × fixture  (factor 4, learned)
game state   = built (heavy favourites sub early), off: no RMSE gain

λ            = xG_against
x_cs_pts     = e^(−λ) · CS_PTS[pos] · p_60                    GK/DEF 4, MID 1, FWD 0
x_app_pts    = p_play + p_60
x_saves_pts  = E[⌊S/3⌋], S ~ Poisson(2.1·λ) · p_start          GK only (1 pt per 3 saves)
dc90         = (DefCon actions + 3·position avg) / (n90 + 3)      this season, FPL
x_defcon_pts = 2 · P(Poisson(dc90 · 82/90) ≥ T) · p_start       T: DEF 10, MID/FWD 12, GK none
x_bonus_pts  = bonus90 · (E[min]/90) · (adj for MID/FWD | P(CS) ÷ his team's usual P(CS) for GK/DEF)
x_deductions = −E[⌊GC/2⌋ | GC ~ Poisson(λ)]·p_start [GK/DEF]  −  yellow90·(E[min]/90)
  • The custom FDR is only shown on the Fixtures page; the model uses the team model's expected goals
  • DefCon counts come from FPL bootstrap-static (CBIT for defenders, CBIRT for midfielders and forwards)
  • For example, Tarkowski at 10.2 per 90 hits the threshold in about 45% of starts
  • Penalty and set-piece duties add a separate term (section 07, live-only); because xG already includes some penalty xG, their weights are learned from outcomes and can shrink toward 0 if they double-count

How the live-only factors learn

  • Penalties, set pieces, return from injury and predicted line-ups can't be backtested: there's no GW-by-GW taker, injury or line-up history. So every player one touches is logged before the deadline (factor_effect_log, migration 0009) with his prediction without the factor and what it adds.
  • After the GW, predict.py records what happened (goals, goals+assists, or started) and refits each weight to best match reality: squared error for goals, Brier for starts. The weight is shrunk toward its starting value (penalty 0.5, set piece 0.5, return 1.0, line-up 0.7) by 40 pseudo-cases.
  • Predicted line-ups and managerial changes come from lineups.py: one Claude Opus 5 call with web search and fetch in the 48h before a deadline (about $1–2 per GW), matched to squads and stored in predicted_lineups and team_context.

4. Team goals model (team_model.py)

  • Every fixture gets both sides' expected goals from two sources, blended
fitted:  E[home xG] = exp(μ + home + att_home + def_away)
         E[away xG] = exp(μ + att_away + def_home)
         fitted on match xG, each match weighted 0.5 ^ (age in days / 90);
         att/def pulled toward a prior by 3 virtual matches (0 for established clubs,
         att −0.25 / def +0.25 for promoted clubs)
odds:    football-data.co.uk market-average 1X2 and over/under 2.5, margin removed;
         total goals solved from P(over 2.5), split solved from P(home) − P(away)
blend:   xG = 0.75·odds + 0.25·fitted where odds are published, else fitted
  • Live, the fit uses last season's matches from the FPL dataset (fpl_history.season_matches) plus this season's matches, rebuilt from FPL's event/{gw}/live (a club's xG in a GW = its players' expected_goals, split evenly across a double)
  • Odds come from fixtures.csv, usually published a few days before each deadline, so only the next round gets them
  • Each projection stores its fixture's team_xg_for, team_xg_against and whether odds were used in components
  • The 90-day half-life and 0.75 odds weight were tuned on 2023/24
  • Blowout guard: a side's xG above 3.0 in one match counts only half of the excess (XG_CAP, XG_OVER), so one 5-xG game can't define a team's attack
    • Example: Man Utd's 5.15 xG vs Ipswich (GW2) counts as 4.08; their attack vs an average side drops 1.74 → 1.65 goals

5. Form and calibration multipliers

  • World Cup form (form.py, one-off): for matched players with ≥ 90 WC minutes, mult = clamp(1 + 0.12 · min(1, min/270) · clamp(GA90 − 0.35, −0.5, 0.8), 0.90, 1.12)
  • It scales xG/90 and xA/90, so it flows through goals, assists and bonus
  • It applies only until the player's club has played its first league game
  • Calibration: every component is multiplied by the position multiplier from model_calibration, so components still sum to x_pts
  • The multiplier is written to components.calibration

6. Range of outcomes (outcomes.py)

  • Each fixture is simulated 2,000 times from the same components, so the simulated average equals x_pts:
    • Minutes: one draw picks 60'+ start / shorter start / cameo / no appearance from P(60), P(start), P(play)
    • Goals and assists ~ Poisson, scaled by the minutes drawn and by a "good or bad day" gamma multiplier (variance DAY_VAR = 1.0)
    • Team goals against ~ Poisson(xG against): clean sheet, −1 per 2 conceded, saves (GK), all as in the points rules
    • DefCon 2 pts with P(threshold); yellow card −1 with his card rate
    • Bonus goes mostly to draws where he scored, assisted or kept a clean sheet; its average equals his projected bonus
  • A double GW adds its fixtures' draws; the position calibration multiplier scales them like x_pts
  • Stored as components.range: P10, median, P90, P(10+ pts) and P(≤ 2 pts); shown in the "i" pop-up and the Captain options card on My Team
  • The captain is still chosen by the average: in the backtest, captaining by P(10+) or by P90 scored less (6.60 and 6.68 vs 7.17 pts per GW)
08

Predictions & calibration (predict.py)

  1. Score. For GWs FPL marks finished that still have unscored prediction_log rows, fetch event/{gw}/live, fill in actual points and minutes, and score each Best XI (starters + captain doubled).
  2. Calibrate. Over scored rows from GW6 on (CALIB_FROM_GW; earlier logs are unusable) with predicted xPts ≥ 2, per position: raw = clamp(Σactual / Σpredicted, 0.5, 2), mult = clamp((n·raw + 3) / (n + 3), 0.8, 1.2) where n = GWs scored. The next model run applies it. With no usable data, every multiplier is reset to ×1.0.
  3. Best XI. For the next GW, solve the single-squad MILP twice, with a £100.0m budget ("capped") and with no budget ("uncapped"). Upsert into gw_predictions, unless that GW is already scored.
  4. News weight. Score logged news cases (did he start?) and refit news_weight (section 12).
  5. Snapshot. Replace the unscored prediction_log rows for that GW with every pool player's predicted xPts. The GW only advances at the deadline, so the last pre-deadline run is the snapshot that gets scored.
  • A GW is scored if either its per-player log or its published Best XI is still unscored
  • The GW1 Best XI (predicted 5.2 under the old minutes bug) is kept as an honest record
09

Optimizer (optimize.py, HiGHS MILP)

Inputs

  • All current-version (rules-v2) projections, giving xp_by_gw[player][gw]. The plan's GWs are the first horizon distinct GWs in the table.
  • Pool: players whose status isn't i/s/u/n. Every player's total is summed over the plan horizon only. The universe is your 15 plus, per position, the top candidates by that total (GK 8, DEF 25, MID 25, FWD 15) and the best by points per £ (GK 4, DEF 8, MID 8, FWD 5), so cheap enablers stay available.
  • Team state: the latest user_team_state row by GW. Budget = Σ selling price of your 15 + bank. Selling price = purchase price + half of any rise (rounded down), or the current price after a fall. Purchase prices come from the public entry/{id}/transfers (latest transfer in, ignoring Free Hit weeks), or the GW1 price for players kept from your first squad. An owned player "costs" his selling price in the MILP, so the budget is exactly what you could raise. Free transfers: null means unlimited (preseason), otherwise max(1, value), where the value is rebuilt from history (section 11).
  • Horizon: the argument, else the user's last saved horizon, else 5. Clamped to the GWs available.

Hard constraints (every GW)

  • 15 players: 2 GK, 5 DEF, 5 MID, 3 FWD. At most 3 per club. Squad cost ≤ budget.
  • 11 starters: 1 GK, 3–5 DEF, 2–5 MID, 1–3 FWD. One captain, who must start.
  • Squad transitions: own[g] − own[g−1] = buy[g] − sell[g], starting from your current 15.
  • Free transfers: hits[g] ≥ buys[g] − free[g]. free[0] ≤ FT; after that, free[g] ≤ free[g−1] − used + 1, capped at 5. Preseason, the first GW is unlimited and the next starts at 1.

Objective

maximise  Σ_g 0.9^g · Σ_i xp[i,g] · (start[i,g] + captain[i,g] + 0.1·bench[i,g])
          − 4 · Σ_g hits[g]
  • The solver runs with a 1% relative gap and a time limit of min(300, 45 + 7·H) seconds
  • Output per GW: transfers in and out, hits, banked FTs, XI points including the captain
  • Reported "planned points" are undiscounted
  • "Gain" is plan points minus holding the current 15 with the best XI and captain each week
  • based_on stores the squad the plan used, so the web can flag it as stale after a team change
  • Each GW's squad also marks a vice-captain (next-best starter) and a bench order: the sub GK first, then outfield subs by projected points

Other modes

  • --fresh: best 15 from scratch for £100m
  • --transfers: single-deadline swap valued over the horizon
  • Both reuse the single-squad _solve, which the Best XI and chip evaluators also use
10

Chip timing

  • Each chip comes twice a season: one set for GW1–19, lost if unused by the GW19 deadline, and a fresh set for GW20–38
  • Each copy is valued as its marginal gain over the squad you would field on the planned transfer path, scanned across the GWs of its own half that fall in the horizon
  • The best GW per copy is kept
ChipGain at GW gBar
Triple CaptainCaptain's xPts that GW (one extra ×1)12
Bench BoostSum of the 4 bench players' xPts18
WildcardFresh optimal 15 for GWs g…end − planned path over the same window + 4 × hits the path takes from g8
Free HitOne-week optimal 15 at GW g − the planned squad at g8
  • Per-week options: every chip stores an option for each GW it scanned
  • Triple Captain: the captain
  • Bench Boost: the 4 bench players
  • Wildcard / Free Hit: the full new squad (XI, captain) plus exactly which players go out and in versus your planned squad that week
  • The Chips tab reads these, so you can see the moves for any week, not only the best one
  • A chip is recommended only if you still hold it and its gain clears the bar
  • Use it or lose it: when the horizon reaches GW19, a first-half chip you still hold has its bar dropped to 0, so it gets recommended at its best remaining window
  • If the horizon stops short of GW19, the "hold" advice names the first-half chips that will expire
  • If several do, the one with the largest gain over its bar wins
  • Otherwise the advice is "hold"
  • DGW and BGW labels are attached only when the fixture list confirms them: a GW where a club plays twice is a DGW, one where clubs have no fixture is a BGW
  • Available chips = the four codes minus any chip played in the same half as the next deadline
11

Team sync & personalisation

  • Scheduled sync (sync_team.py): for "me" and every profile, read entry, history and picks for current_event, then upsert user_team_state for that GW. Stored: bank, value, rank, chips, and free transfers for the next deadline, rebuilt from history.current: the first GW played is unlimited, then +1 per GW capped at 5, minus free transfers used (transfers − hit cost ÷ 4). Wildcard and Free Hit weeks keep the banked transfers. Preseason, squads are private, so it keeps or copies the latest snapshot for the same entry.
  • Manual sync (POST /api/sync): the same logic for the logged-in user, then dispatches fpl-optimize.
  • Screenshot upload (POST /api/team-upload): Claude Haiku reads 15 names, roles and armbands through a forced tool call. Names are matched to web_name by exact match after accent folding, then by substring. At least 11 matches are needed. Preseason it's saved as gw = 0 with all chips. In-season it's saved as the latest synced GW + 1, with bank, free transfers and chips carried over, so it overrides the synced squad until that deadline, when FPL's real picks replace it. Uploaded rows have no fpl_entry_id. Then re-optimized.
  • On-demand optimize (POST /api/optimize, signed in): validates horizon 1–38 and dispatches the workflow for that user. The Optimizer page polls optimizer_runs until the new plan lands, in about 1–2 minutes.
  • Stale plan warning: if the current squad's IDs differ from transfers.based_on, the Optimizer page warns instead of showing old transfers.

News & sentiment

  • Targets: players with an FPL flag (status not "a", or a chance-of-playing value) plus anyone owned by ≥ 5%, flagged players first, capped at 200
  • For each: Google News query "web_name" Club football (injury OR fitness OR lineup OR transfer OR Premier League), up to 5 headlines from the last 21 days, then Claude Haiku 4.5 with a forced record_sentiment tool
  • It returns sentiment, topics (injury-risk, return-from-injury, rotation, suspension, form-buzz, transfer, off-pitch, none), minutes_risk_adj in [−1, 0], and a one-line summary
  • Results tagged "none" are dropped
  • The table is replaced in full each run (97 rows on the last run)
  • Except when more than half the classifications fail (API down or out of credits): the job then keeps the last good set and fails the step
  • Since rules-v4, news lowers availability in the model (formula in section 07). It is shown in the Players table, the "i" pop-up and the assistant.
  • news_weight (default 1.0) is re-learned every run. predict.py logs each news-affected player before the deadline (news_effect_log). After the GW it records whether he started, then picks the weight whose start probabilities best match reality (Brier score), shrunk toward 1.0 by 30 pseudo-cases. The result is stored in model_params.
  • Historical news isn't available from free sources, so news can't be backtested on past seasons; it improves from live outcomes instead.
  • Needs migration 0008_model_params_news_log.sql. Until then the weight stays at 1.0 and logging is skipped.

  • Each step ships only if the backtest shows it improves accuracy
  • The ordering puts the biggest expected error reduction for the effort first

Keeping this current

  • This file, web/content/architecture.html, is the single source for both the in-app Docs tab and the Claude artifact
  • The rule in fpl-selector/CLAUDE.md:
  1. Any commit that changes behaviour in worker/, web/, mobile/, supabase/ or .github/workflows/ updates the affected sections here in the same commit. That includes formulas, parameters, pipeline steps, tables, routes and known issues (move fixed ones out).
  2. Bump the doc revision and date in the header, and add a History entry.
  3. Republish the Claude artifact from this file (Artifact tool, publish with the saved artifact URL). The in-app tab updates on the next Vercel deploy.
