FPL Selector Blueprint

How the app is built and how it picks players: every data source, pipeline step, formula, optimizer constraint and parameter behind the buy, sell, captain and chip advice. It describes what the code does today, including where that differs from what it was meant to do.

01

Overview

FPL Selector is a personal Fantasy Premier League assistant. It pulls official FPL data and last-season Understat xG, projects expected points (xPts) for every player in every remaining gameweek with a transparent rules-based model, then runs a mixed-integer optimizer over your squad to recommend transfers, captain, hits and chip timing. A news layer and a grounded Claude chat assistant sit on top.

PlayersSortable table of every player with next-GW xPts, multi-GW sum, component breakdown drawer and news chip.
Fixtures8-GW ticker coloured by the custom 1–5 FDR.
My TeamYour 15 on a pitch, synced from FPL or read from a screenshot.
OptimizerMulti-week transfer path, hits, captain and chip windows over a horizon you choose.
Best XIBest single-GW squad (£100m and uncapped), scored afterwards to calibrate the model.
AssistantClaude chat that can only cite numbers returned by its data tools.
Guide · SettingsUser help page; FPL entry ID and manual sync.
DocsThis page. Visible only to the owner account.

Design principles (from CLAUDE.md): every xPts number is a sum of stored, named components; minutes come first; underlying stats are fixture-adjusted and shrunk toward base rates; recommendations reason about the real team state (bank, free transfers, chips); sentiment stays advisory until backtested.

06

Crosswalk & custom FDR

FPL ↔ Understat player matching (crosswalk.py)

No shared ID exists, so names are fuzzy-matched after ASCII-folding.

  1. Team pass. Candidates are restricted to the player's club, with five team names mapped (Man City, Man Utd, Newcastle, Nott'm Forest, Spurs). Score = max of token_sort_ratio on full name and web name, and partial_ratio on web name when it has 5+ letters. A surname match plus a compatible first name raises the score to 91. Accept if the score is ≥ 85 and beats the runner-up by ≥ 6.
  2. Global pass (summer transfers): full-name token_sort_ratio ≥ 92 against all Understat players, margin ≥ 8.
  3. Anything else goes to reports/crosswalk_review.csv. The last run matched 396 players (51 via the global pass) and left 271 unmatched: 162 low score, 108 at promoted clubs, 1 ambiguous.

Every run clears understat_id first, so dropped matches don't linger.

Custom fixture difficulty (fdr.py)

Team xG for and against per game pools 2025/26 Understat (38 games at half weight) with this season's FPL numbers: xG for = Σ players' expected_goals, xG against = Σ players' expected_goals_conceded ÷ 11, because all 11 players on the pitch accrue every chance conceded. Team rating = xG for − xG against. Promoted clubs use this season alone, or the weakest returning team's rating before their first game. For each fixture, difficulty = 1 + 4 × (opponent rating − min) / (max − min), then −0.25 at home and +0.25 away, clamped to 1–5. Current range: Arsenal +1.17 (hardest opponent) down to Sunderland −0.45.

07

The xPts model (model.py, rules-v2)

For every player and every fixture in the horizon, the model computes eight components and sums them. Double gameweeks sum both fixtures. Blank gameweeks write no row. The next GW is FPL's is_next event (the next deadline), and the pipeline writes every GW from there to GW38. Each run also deletes projections for GWs that have started, so "lowest GW in projections" is always the next deadline.

1. Minutes

availability = 0            if status in {i, s, u, n}
             = chance/100   if chance_of_playing_next_round is set
             = 0.5          if status = d
             = 1.0          otherwise
history      = last 8 finished GWs in which the player's club played: {games, starts, minutes}
w(GW)        = 0.5 ^ (GWs ago / 3)                                  recent games count most
prior        = min(1, last_season_understat_minutes / 2600)          (none if unmatched)
start_rate   = (Σw·starts + 0.5·prior) / (Σw·games + 0.5)             prior alone before any game
p60_start    = share of full-start GWs with 60+ min     }  each shrunk toward its default
start_mins   = average minutes in those starts          }  (0.88, 85, 0.15, 20 min)
cameo_rate   = share of non-start GWs with a sub cameo  }  by 3 virtual games
cameo_mins   = average cameo minutes                    }
p_start      = availability × start_rate
p_cameo      = (1 − p_start) × cameo_rate      (0 if unavailable)
p_play       = min(1, p_start + p_cameo)
E[minutes]   = p_start·start_mins + p_cameo·cameo_mins
p_60         = p_start · p60_start

Live, the history comes from FPL's event/{gw}/live (one call per GW, 8 per run); in the backtest, from the dataset rows. Only GWs where the player's current club played count, so a club blank isn't read as being dropped. The half-life (3 GWs) and prior strength (0.5 games) were tuned on 2023/24 and confirmed on the held-out 2024/25 and 2025/26.

2. Attacking rates, shrunk to base (empirical Bayes)

base[pos]  = minutes-weighted xG/90 and xA/90 over all matched players at that position
sample     = 0.5 × last season (Understat xG, xA, minutes) + this season (FPL xG, xA, minutes)
n90        = sample minutes / 90
xg90       = (sample xG + 12·base_xg90) / (n90 + 12)      K = 12 "virtual" full matches
xa90       = (sample xA + 12·base_xa90) / (n90 + 12)
yellow90   = last season's yellow-card rate  (0 if unmatched)
no data in either season → 0

A 90 from last season counts half as much as a 90 from this season, so current form takes over as the season goes on. Players with no Understat match (promoted clubs, arrivals from abroad, about 40% of the list) use this season's FPL numbers alone.

3. Per-fixture components

adj          = opp_xGA_pg / league_avg_xGA_pg × (1.05 home | 0.95 away)
x_goals_pts  = xg90·form · (E[min]/90) · adj · GOAL_PTS[pos]      GK/DEF 6, MID 5, FWD 4
x_assist_pts = xa90·form · (E[min]/90) · adj · 3

λ            = (0.5·opp_xGF_pg + 0.5·own_xGA_pg) × (0.9 home | 1.1 away)
x_cs_pts     = e^(−λ) · CS_PTS[pos] · p_60                    GK/DEF 4, MID 1, FWD 0
x_app_pts    = p_play + p_60
x_saves_pts  = (2/3)·λ·p_start                                GK only
dc90         = (DefCon actions + 3·position avg) / (n90 + 3)      this season, FPL
x_defcon_pts = 2 · P(Poisson(dc90 · 82/90) ≥ T) · p_start       T: DEF 10, MID/FWD 12, GK none
x_bonus_pts  = min(1.5, 0.25 · (goals + assists [+ CS for GK/DEF]))
x_deductions = −E[⌊GC/2⌋ | GC ~ Poisson(λ)]·p_start [GK/DEF]  −  yellow90·(E[min]/90)

Team xG for/against per game comes from the blended team ratings in section 06. The custom FDR is only shown on the Fixtures page; the model uses the opponent's xG conceded directly. DefCon counts come from FPL bootstrap-static (CBIT for defenders, CBIRT for midfielders and forwards). For example, Tarkowski at 10.2 per 90 hits the threshold in about 45% of starts. Penalty and set-piece flags are deliberately unused: both Understat and FPL xG already include penalty xG, so a bonus would double-count.

4. Form and calibration multipliers

World Cup form (form.py, one-off): for matched players with ≥ 90 WC minutes, mult = clamp(1 + 0.12 · min(1, min/270) · clamp(GA90 − 0.35, −0.5, 0.8), 0.90, 1.12). It scales xG/90 and xA/90, so it flows through goals, assists and bonus. It applies only until the player's club has played its first league game.

Calibration: every component is multiplied by the position multiplier from model_calibration, so components still sum to x_pts. The multiplier is written to components.calibration.

08

Predictions & calibration (predict.py)

  1. Score. For GWs FPL marks finished that still have unscored prediction_log rows, fetch event/{gw}/live, fill in actual points and minutes, and score each Best XI (starters + captain doubled).
  2. Calibrate. Over scored rows from GW6 on (CALIB_FROM_GW; earlier logs are unusable) with predicted xPts ≥ 2, per position: raw = clamp(Σactual / Σpredicted, 0.5, 2), mult = clamp((n·raw + 3) / (n + 3), 0.8, 1.2) where n = GWs scored. The next model run applies it. With no usable data, every multiplier is reset to ×1.0.
  3. Best XI. For the next GW, solve the single-squad MILP twice, with a £100.0m budget ("capped") and with no budget ("uncapped"). Upsert into gw_predictions, unless that GW is already scored.
  4. Snapshot. Replace the unscored prediction_log rows for that GW with every pool player's predicted xPts. The GW only advances at the deadline, so the last pre-deadline run is the snapshot that gets scored.

A GW is scored if either its per-player log or its published Best XI is still unscored. The GW1 Best XI (predicted 5.2 under the old minutes bug) is kept as an honest record.

09

Optimizer (optimize.py, HiGHS MILP)

Inputs

  • All current-version (rules-v2) projections, giving xp_by_gw[player][gw]. The plan's GWs are the first horizon distinct GWs in the table.
  • Pool: players whose status isn't i/s/u/n. Every player's total is summed over the plan horizon only. The universe is your 15 plus, per position, the top candidates by that total (GK 8, DEF 25, MID 25, FWD 15) and the best by points per £ (GK 4, DEF 8, MID 8, FWD 5), so cheap enablers stay available.
  • Team state: the latest user_team_state row by GW. Budget = Σ selling price of your 15 + bank. Selling price = purchase price + half of any rise (rounded down), or the current price after a fall. Purchase prices come from the public entry/{id}/transfers (latest transfer in, ignoring Free Hit weeks), or the GW1 price for players kept from your first squad. An owned player "costs" his selling price in the MILP, so the budget is exactly what you could raise. Free transfers: null means unlimited (preseason), otherwise max(1, value), where the value is rebuilt from history (section 11).
  • Horizon: the argument, else the user's last saved horizon, else 5. Clamped to the GWs available.

Hard constraints (every GW)

  • 15 players: 2 GK, 5 DEF, 5 MID, 3 FWD. At most 3 per club. Squad cost ≤ budget.
  • 11 starters: 1 GK, 3–5 DEF, 2–5 MID, 1–3 FWD. One captain, who must start.
  • Squad transitions: own[g] − own[g−1] = buy[g] − sell[g], starting from your current 15.
  • Free transfers: hits[g] ≥ buys[g] − free[g]. free[0] ≤ FT; after that, free[g] ≤ free[g−1] − used + 1, capped at 5. Preseason, the first GW is unlimited and the next starts at 1.

Objective

maximise  Σ_g 0.9^g · Σ_i xp[i,g] · (start[i,g] + captain[i,g] + 0.1·bench[i,g])
          − 4 · Σ_g hits[g]

The solver runs with a 1% relative gap and a time limit of min(300, 45 + 7·H) seconds. Output per GW: transfers in and out, hits, banked FTs, XI points including the captain. Reported "planned points" are undiscounted. "Gain" is plan points minus holding the current 15 with the best XI and captain each week. based_on stores the squad the plan used, so the web can flag it as stale after a team change. Each GW's squad also marks a vice-captain (next-best starter) and a bench order: the sub GK first, then outfield subs by projected points.

Other modes

--fresh: best 15 from scratch for £100m. --transfers: single-deadline swap valued over the horizon. Both reuse the single-squad _solve, which the Best XI and chip evaluators also use.

10

Chip timing

Each chip comes twice a season: one set for GW1–19, lost if unused by the GW19 deadline, and a fresh set for GW20–38. Each copy is valued as its marginal gain over the squad you would field on the planned transfer path, scanned across the GWs of its own half that fall in the horizon. The best GW per copy is kept.

ChipGain at GW gBar
Triple CaptainCaptain's xPts that GW (one extra ×1)12
Bench BoostSum of the 4 bench players' xPts18
WildcardFresh optimal 15 for GWs g…end − planned path over the same window + 4 × hits the path takes from g8
Free HitOne-week optimal 15 at GW g − the planned squad at g8

A chip is recommended only if you still hold it and its gain clears the bar. Use it or lose it: when the horizon reaches GW19, a first-half chip you still hold has its bar dropped to 0, so it gets recommended at its best remaining window. If the horizon stops short of GW19, the "hold" advice names the first-half chips that will expire. If several do, the one with the largest gain over its bar wins. Otherwise the advice is "hold". DGW and BGW labels are attached only when the fixture list confirms them: a GW where a club plays twice is a DGW, one where clubs have no fixture is a BGW. Available chips = the four codes minus any chip played in the same half as the next deadline.

11

Team sync & personalisation

  • Scheduled sync (sync_team.py): for "me" and every profile, read entry, history and picks for current_event, then upsert user_team_state for that GW. Stored: bank, value, rank, chips, and free transfers for the next deadline, rebuilt from history.current: the first GW played is unlimited, then +1 per GW capped at 5, minus free transfers used (transfers − hit cost ÷ 4). Wildcard and Free Hit weeks keep the banked transfers. Preseason, squads are private, so it keeps or copies the latest snapshot for the same entry.
  • Manual sync (POST /api/sync): the same logic for the logged-in user, then dispatches fpl-optimize.
  • Screenshot upload (POST /api/team-upload): Claude Haiku reads 15 names, roles and armbands through a forced tool call. Names are matched to web_name by exact match after accent folding, then by substring. At least 11 matches are needed. Preseason it's saved as gw = 0 with all chips. In-season it's saved as the latest synced GW + 1, with bank, free transfers and chips carried over, so it overrides the synced squad until that deadline, when FPL's real picks replace it. Uploaded rows have no fpl_entry_id. Then re-optimized.
  • On-demand optimize (POST /api/optimize, signed in): validates horizon 1–38 and dispatches the workflow for that user. The Optimizer page polls optimizer_runs until the new plan lands, in about 1–2 minutes.
  • Stale plan warning: if the current squad's IDs differ from transfers.based_on, the Optimizer page warns instead of showing old transfers.
12

News & sentiment (advisory)

Targets: players with an FPL flag (status not "a", or a chance-of-playing value) plus anyone owned by ≥ 5%, flagged players first, capped at 200. For each: Google News query "web_name" Club football (injury OR fitness OR lineup OR transfer OR Premier League), up to 5 headlines from the last 21 days, then Claude Haiku 4.5 with a forced record_sentiment tool. It returns sentiment, topics (injury-risk, return-from-injury, rotation, suspension, form-buzz, transfer, off-pitch, none), minutes_risk_adj in [−1, 0], and a one-line summary. Results tagged "none" are dropped. The table is replaced in full each run (97 rows on the last run).

The signal is shown in the Players table and the assistant's player lookup. It does not change xPts or the optimizer.

Assistant (/api/assistant)

Claude Haiku 4.5 with up to 6 tool rounds. The system prompt forbids stating numbers a tool didn't return, requires citing them, and routes "what should I do" questions to the optimizer plan. Signed-in users only: logged-out requests get 401, because every call spends Anthropic credits. There is no rate limit per user.

Web app & auth

  • Server components read Supabase with the anon key. My Team and Optimizer need a signed-in user and read only that user's rows; logged-out visitors get a login prompt.
  • The proxy (web/proxy.ts, Next 16's name for middleware) refreshes the Supabase session cookie on every non-asset request.
  • The assistant endpoint needs a signed-in user. Login is email and password. Supabase has email auto-confirm on, so addresses aren't verified.
  • The Docs tab (/docs) and its content route (/docs/content) return 404 unless the signed-in user's email is savalgiabhilash@gmail.com (web/lib/owner.ts). The nav shows the tab only for that account. The page source is web/content/architecture.html, which is outside public/, so it is never served statically.
  • The mobile app (mobile/) reads the same tables. Players is public. My Team signs in with the same email and password accounts as the website (supabase.auth.signInWithPassword), keeps the session in AsyncStorage, refreshes its token only while the app is in the foreground, and shows the signed-in user's own squad. Accounts are created on the website.

Known issues (review of 2026-09-25)

Found by reading the code and checking the live Supabase data and the /best page. Every issue except H7 (a Supabase dashboard setting) is fixed.

H1·3·4·8

Fixed Current-season data, chip halves, selling prices, uploads

H1: matched players ignored this season's xG and the World Cup factor never switched off (fixed: pooled sample, factor preseason only). H3: chips assumed one set per season (fixed: per-half availability and a GW19 use-it-or-lose-it rule). H4: the budget used current prices (fixed: real selling prices from transfer history). H8: in-season uploads were ignored (fixed: saved as the next GW).

H2·5·6

Fixed Zero attackers, pipeline order, open assistant

H2: 271 unmatched players projected zero attacking output (fixed: fall back to this season's FPL xG/xA). H5: the optimizer ran before team sync (fixed: sync first). H6: /api/assistant was open to anyone (fixed: signed-in users only).

C1–4

Fixed Critical issues from the first review

C1: the app was stuck on GW1 because old projections were never deleted (fixed: is_next GW, prune started GWs). C2: projections were about 5× too low because this season's minutes were divided by a full season (fixed: minutes share per club game, blended with last season). C3: calibration learned from a stale Aug 9 snapshot and the Best XI was reset to unscored each run (fixed: replace snapshots, never reopen scored GWs, calibrate from GW6). C4: free transfers stored transfers made (fixed: rebuilt from history in worker and /api/sync).

H7

High Unverified emails

Factors & accuracy plan

This section lists everything that currently shapes a recommendation, what is left out, and a plan to make the predictions as accurate as the free data allows. FPL points are noisy (one goal swings a score by 4–6), so "most accurate" only means something against a benchmark. The plan therefore starts by measuring.

Optimizer factors: horizon (you choose), 0.9 per-GW discount, bench at 0.1 weight, −4 per hit, free-transfer rollover (cap 5), selling prices, £ budget, 3-per-club, formation, two chip sets with GW19 expiry and fixed bars (TC 12, BB 18, WC 8, FH 8), DGW/BGW flags.

Left out: bookmaker odds, predicted line-ups, European and cup fixture congestion, penalty order as its own term, news sentiment (advisory by design), price changes, effective ownership, and uncertainty (every number is a single expected value).

Backtest results

python -m fpl_worker.backtest replays the production model over every gameweek of 2023/24–2025/26. It uses only what was known before each deadline (previous season + this season to GW−1) and scores against actual points, with FPL's own xP as the benchmark. Results go to worker/reports/. It calls model.py/fdr.py directly, so any model change is measured by rerunning it.

Head-to-head covers 2023/24 and 2024/25 (55,661 player-GWs). The dataset's xP is broken for 2025/26 (it averages 34% of actual points), so the harness drops it there automatically. Three differences favour xP. The dataset has no injury flags, so the replay treats everyone as available. "Last season" uses FPL xG instead of Understat. And when xP was recorded isn't documented, so it may include team news the replay can't see. For a clean head-to-head from now on, log FPL's ep_next next to each live prediction (needs a prediction_log column).

rules-v2 (minutes model, step 1): over all three seasons, MAE 1.117 → 1.035 (−7.3%), rank correlation 0.633 → 0.680, P(start) Brier 0.114 → 0.097 (−15%), top-20 no-shows 10% → 7%, top-20 points 4.55 → 4.77. It improves on every season, including the held-out 2024/25 and 2025/26. The one metric that got worse, MAE among players who played (+2%), is conditioned on the outcome; the model's job is the unconditional forecast. Still behind FPL xP, which has injury news the replay lacks.

What the rules-v1 baseline said to fix first: minutes (10% no-shows in the top 20; recent absences aren't weighted) and ranking outside the top one or two players (team-level goal expectations and player shares). Those are steps 1–3.

The plan, in order

Each step ships only if the backtest shows it improves accuracy. The ordering puts the biggest expected error reduction for the effort first.

#StepWhat changesWhy it matters
0Measure firstA backtest harness on the vaastav dataset (every GW of 2022/23–2025/26, with FPL's own xP at the time and actual points). Replay the model using only data available before each deadline. Report MAE and RMSE per position, rank correlation among likely starters, top-50 hit rate, calibration by decile, Brier score for P(start) and P(60+), and decision scores (captain and Best XI points vs actual). Log per-component predictions live (goals, assists, CS, saves, bonus, DefCon, minutes) against event/{gw}/live.Without this, no change can be called an improvement. FPL's ep_next is the benchmark to beat.
1Minutes model Done · rules-v2Recency-weighted starts and minutes from each player's GW history (half-life about 3 GWs). Separate P(start), P(60+ | start) and cameo minutes per player. Return-from-injury ramp. Rotation factor for clubs with a midweek European or cup match. The news minutes_risk_adj is adopted only if it improves the Brier score.A non-starter scores 0–1, so minutes errors are the largest single source of misses.
2Team goals model + oddsFit a time-decayed Dixon-Coles Poisson model on match xG and goals, with home advantage estimated from data. Blend with bookmaker match and totals odds (The Odds API free tier, about 2 calls per GW), with the blend weight set by the backtest. Output: each side's expected goals per fixture.One coherent number drives goals, assists, clean sheets, goals conceded, saves and bonus. Odds are the sharpest public forecast.
3Player sharesPlayer goals = team expected goals × the player's recency-weighted share of team non-penalty xG while on the pitch, and the same for assists. Penalties become a separate term: FPL penalties_order × team penalty rate × about 0.78 conversion.Shares are more stable than raw per-90s, and a new penalty taker is priced immediately.
4Component modelsBonus: expected BPS from components, then rank within the match, via simulation. DefCon: negative binomial, with an opponent-possession effect. Saves: a shots-on-target-against model. Card rates shrunk per player.Removes the remaining crude proxies. Bonus alone is about 10% of points.
5Simulation & uncertaintyMonte Carlo each fixture (team goals → scorers and assisters → CS, bonus) to get each player's full distribution: mean, P10/P90 and P(≥ 10 pts), with teammates correlated.Captain and Triple Captain choices depend on upside, not just the mean.
6Learned correctionReplace the single per-position multiplier with per-component isotonic calibration. Then fit a gradient-boosted residual model on backtest features, shown as its own "correction" component so the breakdown stays explainable.Captures patterns the rules miss, without giving up transparency.

Decision quality (optimizer)

  • Tune the 0.9 discount, the hit threshold and the chip bars on backtested decisions, not intuition.
  • Replace the flat 0.1 bench weight with each bench slot's expected autosub value: P(a starter misses) × that sub's points, in bench order.
  • Price-change model from net transfers (transfers_in_event / transfers_out_event), so buy and sell timing can protect team value.
  • Captaincy with effective ownership and a rank-goal toggle, using the step 5 distributions.

Other ideas

What-if planner (pin or ban players, then re-solve), deadline alerts with the plan and flagged injuries, and a mini-league rivals view.
